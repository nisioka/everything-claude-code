# テスト観点生成

## User Input

```text
$ARGUMENTS
```

## Goal

現在のブランチの変更差分を分析し、手動テストで確認すべきテスト観点をmarkdownファイルとして出力する。

## Execution Steps

### 1. 変更内容の把握

以下のコマンドで変更内容を取得する:
```bash
git diff develop...HEAD --stat
git diff develop...HEAD
```

必要に応じて変更ファイルを読み、影響範囲を把握する。

### 2. 変更の影響分析

変更内容から以下を特定する:
- **変更されたレイヤー**: Resource / Service / Repository / Entity / DTO / Config 等
- **影響を受けるユーザー操作**: CRUD操作、画面表示、バリデーション、認証等
- **データ整合性リスク**: DB変更、フェッチ戦略変更、クエリ変更等
- **副作用の可能性**: 通知、非同期処理、外部連携等

### 3. テスト観点の生成

以下の方針で観点を作成する:

- UTで確認済みのロジック詳細は省略し、画面操作・API実行で確認すべき観点に集中する
- 変更箇所に直結する操作を優先する
- 各観点は「操作」と「確認ポイント」を簡潔に記載する
- 観点数は10〜20程度に収める
- 変更の種類に応じてグループ化する

### 4. ファイル出力

`$ARGUMENTS` で指定されたパスに出力する。指定がなければプロジェクトルートの `test-plan.md` に出力する。

## Output Format

```markdown
# テスト観点

## [カテゴリ1]

| # | 観点 | 操作 | 確認ポイント |
|---|------|------|-------------|
| 1 | ... | ... | ... |

## [カテゴリ2]

| # | 観点 | 操作 | 確認ポイント |
|---|------|------|-------------|
| N | ... | ... | ... |
```

## Notes

- パフォーマンス改善の場合、機能的な観点に加え「改善前と同等以上の速度か」の観点も含める
- バリデーション変更の場合、正常系・異常系の両方を含める
- Entity変更（フェッチ戦略等）の場合、関連する画面操作を洗い出す
